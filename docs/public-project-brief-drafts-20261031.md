# Save and Resume Project Brief — 31 October 2026

The public `/project-brief/` page adds optional **Save draft**, **Review saved draft**, and **Clear draft** controls. A visitor can save an incomplete requirements draft, leave, return, review its saved values and manually choose **Restore empty fields**. Nothing is restored on page load. Populated fields are always preserved, including values supplied by an entry workflow or the existing Shortlist and Readiness handoffs. Closing the saved draft review leaves the form unchanged.

One localStorage key, `bgg_public_project_brief_draft_v1`, contains exactly `{version:1,savedAt:ISO_UTC,fields:{interest,businessType,briefProblem,briefFeatures,briefBudget,briefDate,quoteCurrency}}`. Only a manual Save draft writes it. Contact name, email, phone, business country, contact method, time zone, contact date/time, hidden submission payloads, source IDs and portfolio attribution are excluded. Requirements text is stored as entered, so the interface explains that it must not contain personal or confidential information. This is device/browser-profile storage, available to others using that profile; it is not a server draft, a customer account, encrypted storage or a quotation. The last saved time is labelled as the device's time zone.

Service labels are saved and restored by exact option text because CRM and ERP currently share the same HTML option value. Fixed service, business-type and currency allowlists, exact schema keys, supported version, bounded text lengths, valid calendar dates and a bounded ISO timestamp are checked before a saved copy can be reviewed. Unknown fields (including contact fields), arrays where strings are expected, malformed/oversized data and unsupported versions are rejected without replacing the saved copy. The visitor may explicitly Clear draft to remove an unreadable copy. Saved text is rendered with textContent, never HTML.

Review lists each saved value and whether it can fill an empty field, matches the current value, or will be skipped. Existing values, disabled options and country-derived currency restrictions are preserved. A now-past saved launch date remains visible in the review but is not restored. Requirements, available options and date limits are checked again at the restore action; field or storage changes invalidate an open review. Restoring dispatches input/change events so the existing summary stays current and an open PDF preview becomes stale until explicitly updated.

Save writes are read back before reporting success; Clear removes only this key and verifies removal. Blocked storage, quota failures and failed verification preserve the editable form and do not claim success. Cross-tab or back/forward changes require reviewing the latest saved copy before saving over it; current text is preserved. A fresh storage read checks every Save, Clear and Restore. Save and Restore are disabled while the existing form is sending. Before leaving, the browser's native unsaved-change warning is requested for edits made since the current protected snapshot, and for entered contact details that the draft does not save. Browser support and native warning behavior may vary.

Clear draft leaves the current form, Shortlist, Readiness checklist and their pending handoffs unchanged. Form reset or a successful explicit enquiry clears the current form using existing behavior but keeps the saved draft available until the visitor explicitly clears it. Existing contact validation, market/currency controls, explicit Send project brief, submission schema, Shortlist, Readiness and PDF preview controllers are unchanged. The module makes no requests or analytics calls, creates no server records and submits no form. No-JavaScript contact fallbacks remain available.
