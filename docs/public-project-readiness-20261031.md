# Public Project Readiness Checklist — 31 October 2026

The public planning journey adds `/project-readiness/` between Shortlist and Brief. The Shortlist page links to it; the Brief offers an optional new-tab link before the form so an existing in-page draft can stay open. The checklist is optional: existing routes from Shortlist to Brief remain available. The checklist has six topics: first-release scope, content/data, integrations, access/ownership, review/approval responsibilities, and budget/timing. Visitors choose Ready, Need help or Not sure; blank means unanswered. No readiness score, verified approval, agreed scope, price, availability, meeting or delivery promise is inferred.

Choices remain in page memory until **Save checklist**. Only `{version:1,answers:{approved_item_id:approved_choice_code}}` is written to `bgg_public_project_readiness_v1` in this origin's localStorage. There is no free text, contact information, account access, draft text, cookie, backend request or analytics in this module. Public guidance comes from the six reviewed entries in scripts/public-readiness-items.json. The key is browser/profile specific. **Clear** removes only the checklist key and this tab's readiness handoff; the existing shortlist and other storage are preserved.

After saving, the visitor explicitly selects which answered items to discuss. **Review selected notes in brief** writes a one-time fixed-choice handoff under `bgg_public_project_readiness_handoff_v1` and opens the existing Brief review panel. It does not fill a brief field. **Use readiness notes** is a separate manual action that appends only the selected responses to Features / integrations, labelled as visitor responses. Existing text is preserved. **Cancel readiness review** leaves the brief unchanged. Unselected answers do not enter the brief. The ordinary full-brief review, Preview/PDF and explicit Send remain intact.

Both storage schemas have bounded sizes, exact keys, fixed IDs/codes and supported versions. Unknown IDs, extra personal-data fields, arrays instead of codes and malformed payloads are rejected without silent replacement. Storage failures keep the current choices visible and prevent a false saved state or handoff. Other-tab changes reload clean state and clear note selections; a dirty draft is preserved and requires manual Reload saved checklist. Current saved context is checked again before Save, handoff and Use. Stale or invalid handoffs cannot change fields. The one-time handoff is removed and verified before applying text.

Existing 1,100-character features limits apply without truncation. Exact duplicate notes are skipped. If the brief already has a different fixed response for a selected topic, the visitor must review/remove the earlier note before adding the new one; the module never silently replaces visitor text. These notes do not confirm an approval or client agreement. Shortlist and readiness handoffs use separate keys and can be reviewed independently in the same brief. Readiness input events update the existing summary and invalidate an already-open print preview through its existing mechanism.

The feature adds a native static page, three scoped assets, a public guidance manifest and deterministic builder. Existing application controllers, backend, Search catalog, other marketing pages, CRM and automations remain unchanged. Of the existing pages, only Brief receives the readiness assets; Shortlist receives one navigation link in its native and existing source-rendered versions.
