# Follow-up task center

Private Bandevi staff workspace only. No public travel, B2B, white-label or Call CRM changes.

The inbox Tasks link opens /team-inbox/tasks/. Tasks require an accessible real enquiry and may link to its existing project or a specific proposal revision. A task records a title, active staff owner, India-calendar due date, Low/Normal/High priority and optional internal notes. Task dates do not replace the existing single enquiry follow-up date. No email or customer notification is sent by task actions.

The queue includes Open, Overdue, Due today, Next 7 days, Completed and All tasks. Tomorrow through today + 7 days is upcoming; earlier dates are overdue. Exact My tasks ownership and priority filters apply to both counts and rows; text search affects rows independently of counts. Search covers title, reference and owner. Pages contain 25 tasks ordered consistently by state, due date, priority, created time and identifier. Link targets are searched with 25-enquiry results and up to 50 proposal revisions per enquiry.

Agents retain the current enquiry-assignment boundary for all reads and writes. Agents can assign task ownership only to themselves; administrators and managers can choose active staff. An agent owner must already own the linked enquiry. Reassigning the enquiry revokes the previous agent's task access even if an old task still names them; administrators can review and reassign open tasks. Client sessions cannot access staff task APIs. QA enquiries are excluded.

Saving uses an immediate transaction and optimistic version checks. Retrying an identical save is idempotent and does not duplicate activity. Existing task links are immutable. Completion requires a written outcome and makes the task immutable; further work requires a new follow-up. There is no destructive delete or automatic overdue completion. Each actual creation, edit or completion adds one activity event on the linked enquiry, with owner, due date, priority, notes and outcome when recorded. Task UI renders customer and task text through textContent, uses existing staff sessions/CSRF/origin checks, clears private rows on sign-out and guards stale asynchronous reads.

Migration adds only followup_tasks and indexes; startup is repeatable and preserves existing records. Rollback restores application code without deleting task data or restoring an older database. Production requires a clean expected baseline, verified SQLite/application/configuration backup, full GitHub checks, exact merged revision deployment, service health, deployed-asset hashes, anonymous access rejection, backup/monitor health and read-only authenticated mobile/desktop checks.

Validation: six synthetic backend cases cover date boundaries, paging, filtering, idempotence, optimistic conflicts, recorded immutable outcomes, link integrity, active owners, agent reassignment/disablement, client/staff lanes, CSRF/origin and repeat migration. Seven browser scenarios cover navigation, creation, literal script text, filters/reset, read-only completion, timeline, linked project, three viewports and agent selectors. Existing inbox/proposal/public regressions remain in CI.
