Project fit · Scope · Delivery · Cost planning · Questions

When this service is a useful fit

A custom application is worth evaluating when a distinctive workflow, access model or connection between systems cannot be handled well by your existing software. Define the business outcome and the internal owner before choosing features.

For a standard requirement, compare an existing product, configuration or a smaller integration first. A custom build also needs ongoing hosting, maintenance and someone responsible for adoption; include these in the business case.

Define the first-release scope

Use the areas below to agree what the first release must do. Features, access and external connections are confirmed in the project proposal.

Business web applications

Specify the records, screens, statuses and approvals needed for one operational process. Define what users can create, change, review and export.

Customer and partner portals

Plan authenticated access, account ownership, documents, requests and status views. Separate the information available to each type of user.

Dashboards and automation

Agree the source and meaning of each metric. Define triggers, approval requirements, retry behaviour and the person responsible when automation cannot complete.

Connections to existing systems

Assess CRM, ERP, website and third-party data flows. Identify dependencies and test boundaries before committing to an integration.

A delivery plan you can review

Agree the outputs and review owner for each stage before work begins.

  1. 1. Define the problem and users

    Describe the repeated task, current tools and expected outcome. Map the people using the application and the decisions it must support.

  2. 2. Specify a reviewable first release

    Agree screens, records, permissions and test scenarios. Separate essential workflows from later improvements and record external dependencies.

  3. 3. Review working increments

    Check the agreed user journeys using representative data. Include errors, duplicate requests, access restrictions and recovery in acceptance tests.

  4. 4. Plan launch and ongoing ownership

    Agree deployment access, data migration, backups, rollback, documentation, training and support. Record what happens after the first release is accepted.

Integrations and migration

Identify the owner and supported interface of each external system. Scope authentication, data mapping, rate limits, retries and monitoring. An integration is included only when feasibility, provider permissions and responsibilities are confirmed in the written proposal.

For an existing system, agree a field map, data-retention requirements and sample migration checks before a full move. Identify exports, attachments and historical records to retain, and decide how work will continue during cutover.

What affects cost and delivery time?

Cost depends on workflow complexity, user roles, interface design, data volume, integrations, testing and deployment requirements. Compare the first build with ongoing hosting, provider usage, maintenance and future change costs rather than treating them as one undifferentiated amount.

Request a written quotation in GBP, USD or INR. Agree assumptions, exclusions, milestone payments, acceptance and changes before work starts. A planning budget or target date is not a confirmed offer.

Agree ownership and support before launch

Confirm source-code and data rights, third-party licences, hosting access, exports, documentation, training, backup and rollback responsibilities in the contract. Define support hours, escalation routes and the treatment of future changes.

Questions to resolve before commissioning

Use these answers to prepare a focused project discussion.

Should we build custom software or buy an existing product?

Compare the workflow fit, integration effort, total running cost and internal ownership of both options. A smaller configuration or connection may meet the need without a new application.

Can the project start with one workflow?

Yes. Propose a first release with defined users, records and acceptance checks. Additional modules and dates should be agreed after dependencies and priorities are reviewed.

How are budget and delivery dates agreed?

The written proposal should set out scope, assumptions, dependencies, milestones and change control. GBP, USD and INR quotations are available; dates and costs need a project-specific review.

Will we receive the source code and documentation?

Confirm the repository, source-code and data rights, deployment documentation, licences and handover responsibilities in the contract. Public service descriptions do not determine those terms.

What support will the software need after launch?

Agree the hosting owner, backup responsibilities, defect process, support hours, monitoring and any maintenance arrangement. Additional development and provider fees should be identified separately.
